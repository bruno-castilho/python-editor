# packages/db — DBA Reference

> **Maintenance:** any change to `packages/db` (schema, migration, `src/index.ts`,
> `prisma.config.ts`) must be accompanied by an immediate update to this document before
> closing the task.

## Schema overview

Two models: **User** and **Project**.

```prisma
model User {
  id             String   @id          // uuidv7 generated by the caller
  name           String
  lastName       String
  email          String   @unique
  hashedPassword String
  emailVerified  Boolean  @default(false)
  createdAt      DateTime @default(now())
  avatar         String?              // URL or null; never an empty string

  personalProjects     Project[] @relation("PersonalProjects")
  sharedWithMeProjects Project[] @relation("SharedWithMeProjects")
  updatedProjects      Project[] @relation("UpdatedProjects")

  @@map("users")
}

model Project {
  id        String   @id              // uuidv7 generated by the caller
  name      String
  fileId    String                    // reference to an external system

  createdAt DateTime @default(now())
  updatedAt DateTime @default(now()) // updated manually, not via @updatedAt

  createdById String
  createdBy   User @relation("PersonalProjects",  fields: [createdById], references: [id])

  updatedById String
  updatedBy   User @relation("UpdatedProjects",   fields: [updatedById], references: [id])

  sharedWith  User[] @relation("SharedWithMeProjects")

  @@map("projects")
}
```

### Relations and join table

| Relation | Type | Physical table |
|----------|------|----------------|
| `User.personalProjects` ↔ `Project.createdBy` | 1-N | FK `projects.createdById` |
| `User.updatedProjects` ↔ `Project.updatedBy` | 1-N | FK `projects.updatedById` |
| `User.sharedWithMeProjects` ↔ `Project.sharedWith` | N-N | `_SharedWithMeProjects` |

The `_SharedWithMeProjects` table has columns `A` (projectId) and `B` (userId), a composite PK `(A,B)`,
an index on `B`, and `ON DELETE CASCADE` FKs on both columns.

### Existing indexes

- `users.email` — unique index via `@unique`
- `_SharedWithMeProjects (B)` — N-N relation support index (auto-generated)
- PKs: `users.id`, `projects.id`, `_SharedWithMeProjects (A,B)`

There are no `@@index` entries beyond the mandatory ones. Queries with `WHERE` on `createdById`,
`updatedById`, or `fileId` are unindexed — evaluate `@@index` before going to production.

## Project conventions

### Naming
- Models in **PascalCase** singular → tables in **snake_case** plural via `@@map`
- Fields in **camelCase**; physical columns inherit the same casing
- IDs: `String @id`, **uuidv7** value generated by the *caller* — never `@default(uuid())` or `autoincrement()`

### Minimum fields for new models
```prisma
model Example {
  id        String   @id
  createdAt DateTime @default(now())
  // ...
  @@map("examples")
}
```

### Named relations (required when multiple FKs point to the same model)
When more than one FK points to the same model, **each relation needs an explicit name on both sides**.
Omitting the name causes a schema validation error:

```prisma
// Project — two fields → User
createdBy User @relation("PersonalProjects", fields: [createdById], references: [id])
updatedBy User @relation("UpdatedProjects",  fields: [updatedById], references: [id])

// User — two reverse sides
personalProjects Project[] @relation("PersonalProjects")
updatedProjects  Project[] @relation("UpdatedProjects")
```

## How to add or modify models

### Checklist
1. Edit `prisma/schema/schema.prisma`
2. `npm run db:migrate` — enter a descriptive name when prompted
3. `npm run db:generate` — regenerates `prisma/generated/` (`migrate dev` does this automatically in dev)
4. **Update this CLAUDE.md** — schema section, indexes, or pitfalls as appropriate

### Optional field → safe on tables with data
```prisma
avatar String?
```
Resulting migration: `ALTER TABLE "users" ADD COLUMN "avatar" TEXT;` — no risk.

### Required field on a non-empty table → requires care
`prisma migrate dev` rejects `NOT NULL` without a `DEFAULT` when rows exist. Strategies:

**Option 1 — temporary default in the schema:**
```prisma
newField String @default("")
```
Apply, then remove the `@default` and run a second migration.

**Option 2 — two migrations:**
1. Add as `String?`
2. Backfill data manually
3. Second migration: `ALTER COLUMN ... SET NOT NULL`

> Migration `20260409172344_add_updated_by_to_project` added `updatedById NOT NULL`
> without a default because the table was empty at that point — do not repeat this in
> production with existing data.

### New N-N relation
```prisma
// Add on both sides with a unique name
sharedWith User[]    @relation("SharedWithMeProjects")   // on Project
projects   Project[] @relation("SharedWithMeProjects")   // on User
```
Prisma creates `_RelationName` automatically with `CASCADE` on both FKs.

## How to create and apply migrations

### Dev (interactive)
```bash
npm run db:migrate     # prisma migrate dev --config prisma.config.ts
```
Creates a SQL file at `prisma/migrations/<timestamp>_<name>/migration.sql` and applies it.

### Production / CI (non-interactive)
```bash
prisma migrate deploy --config prisma.config.ts
```
Applies all pending committed migrations; never generates new ones.

### Push without a migration (prototyping)
```bash
npm run db:push        # prisma db push --config prisma.config.ts
```
Syncs the schema directly to the database without creating a migration file. **Do not use in production.**

### Destructive migrations — renaming a column
`prisma migrate dev` interprets a rename as drop+add, causing data loss. **Always review the
generated SQL and replace it before confirming.** Real example from this project:

```sql
-- Generated by Prisma (DATA LOSS):
ALTER TABLE "users" DROP COLUMN "avatarUrl";
ALTER TABLE "users" ADD COLUMN "avatar" TEXT;

-- What migration 20260316000000 actually used (no data loss):
ALTER TABLE "users" RENAME COLUMN "avatarUrl" TO "avatar";
ALTER TABLE "users" ALTER COLUMN "avatar" SET DEFAULT NULL;
UPDATE "users" SET "avatar" = NULL WHERE "avatar" = '';
```

## Client — instantiation and exports

```typescript
// src/index.ts
import { PrismaPg } from '@prisma/adapter-pg'
import { env } from '@python-editor/env/server'
import { PrismaClient } from '../prisma/generated/client'

const url = new URL(env.DATABASE_URL)
const schema = url.searchParams.get('schema') ?? undefined  // multi-tenant support

const adapter = new PrismaPg({ connectionString: env.DATABASE_URL }, { schema })
const prisma = new PrismaClient({ adapter })

export * from '../prisma/generated/client'   // all generated types
export * from '@prisma/adapter-pg'
export default { prisma }                    // singleton
```

- `DATABASE_URL` comes from `apps/server/.env.development` (loaded via `prisma.config.ts`)
- The `?schema=` URL parameter selects the Postgres schema — useful for isolated environments
- The `PrismaPg` adapter manages the connection pool — do not call `$connect`/`$disconnect` manually
- The client is a **singleton** — always import the exported object, never instantiate a second `PrismaClient`

### prisma.config.ts
```typescript
dotenv.config({ path: '../../apps/server/.env' })
dotenv.config({ path: '../../apps/server/.env.development', override: false })

export default defineConfig({
  schema:     path.join('prisma', 'schema'),        // directory, not a single file
  migrations: { path: path.join('prisma', 'migrations') },
  datasource: { url: process.env.DATABASE_URL },
})
```

## Pitfalls and anti-patterns

### `updatedAt` without `@updatedAt`
`Project.updatedAt` does **not** use the `@updatedAt` directive. The field is updated manually
by the caller. Adding `@updatedAt` would cause automatic updates on every `update` call,
including ones that should not change `updatedBy`.

### Bank-generated IDs
Never use `@default(uuid())` or `@default(autoincrement())`. IDs are **uuidv7 values generated
by the caller** so the value is known before persistence (useful in tests and in composite
operations that need the ID immediately).

### `prisma/schema/` is a directory
The schema lives at `prisma/schema/schema.prisma`, not `prisma/schema.prisma`. Tools that
assume the default path will fail — always pass `--config prisma.config.ts` or
`--schema prisma/schema/schema.prisma`.

### Generated types are in `prisma/generated/` (not `node_modules`)
The `output = "../generated"` in the generator redirects generated types outside of
`node_modules`. After any schema change, run `npm run db:generate`; never edit files under
`prisma/generated/` manually.

### `noUncheckedIndexedAccess` enabled in TypeScript
Index access returns `T | undefined`. When iterating `findMany` results, use `.map()` or
check existence before accessing by index.
